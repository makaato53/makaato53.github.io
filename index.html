Architecture — 3 layers
Layer 1 · InterfaceLiteLLM · Ollama · Web UI
LiteLLM as model gateway — routes tasks to the right model. Code → Qwen 2.5. Reasoning → DeepSeek. Review → Gemma. Generation → Llama 3. Local via Ollama, cloud SOTA as fallback. HTTP API not Docker socket.
↓
Layer 2 · Agent runtimeLangGraph · Supervisor pattern
LangGraph manages the loop: task in → agent asks model → model picks tool → Python executes → results loop back → model decides next step → final answer. Supervisor node with tool executor, reviewer, and final. Handles state, retries, branching, memory.
↓
Layer 3 · Memory (RAG)ChromaDB · BM25 · sentence-transformers
Hybrid retrieval: embeddings for semantic/meaning similarity, BM25 for exact terms, config names, filenames, experiment IDs. Query → BM25 search → vector search → fuse results. 4 collections: agent traces, tool results, project docs, task results. Persistent to disk.
Design decisions
Why hybrid retrieval
Embeddings good at meaning similarity and natural language. BM25 good at exact keywords — config names, file paths, experiment IDs. Neither alone is enough.
Why LangGraph over raw loop
Stateful interaction, shared state across nodes, retries and branching built in. Higher abstraction — manage steps not individual calls.
Why HTTP API for Ollama
No security risk from Docker socket exposure. Cleaner service boundary. More production-like than daemon access.
3 generic agents + plugins
Core agents: repair, geography, general. Domain-specific logic lives in plugins not agents — keeps the core clean and extensible.
Open questions
Unresolved
How much of agent reliability comes from architecture vs prompt quality? Structured-output enforcement helps — ambiguous prompts compound across steps. Still figuring out where to draw that line.
Considering
Turbopuffer as vector store replacement for ChromaDB — better for sub-10M vector loads, runs on CPU, 16x compression. ChromaDB system RAM is a hard upper bound at scale.
What's next
Conclusion on small models
Running small local models through LiteLLM was the right call for getting the architecture working — cheap, fast to iterate, no API costs. But the ceiling is low. The reliability problems (hallucinated tool calls, inconsistent structured output, reasoning failures on multi-step tasks) aren't prompting problems. They're model capability problems. Small models aren't the answer for a serious agent system.

HUEY model lab · build log active build
Given a fixed 24GB GPU, how much reliable agent capability can be recovered by optimizing a model's memory footprint — then spending the recovered compute on better inference?
Three phases
Phase A · Baseline sweepQwen3.5-9B · BF16 / INT8 / NF4
Inventoried the workstation, picked Qwen3.5-9B (8.95B params) as the base model, and ran a 23-task benchmark across three precisions. NF4 used ~48% less peak GPU memory than BF16 and decoded ~16% faster — promising, but the benchmark was too small to trust on quality.
↓
Phase B · Rigor pass144-task benchmark · paired statistics
Rebuilt the benchmark to 144 held-out tasks with objective scoring — unit tests, JSON Schema, exact-match oracles — instead of trusting a model to grade its own output. NF4 accuracy came in 2.8 points below BF16, but the 95% confidence interval crossed zero: not statistically clear either way. The real finding was memory — NF4 left room for ~16 concurrent candidates vs. ~4 for BF16.
↓
Phase C · Inference-time scalingcandidate generation · executable verification
Current phase. If one NF4 pass is slightly worse than one BF16 pass, can several NF4 candidates plus objective verification (unit tests, schema checks, deterministic oracles) beat BF16 anyway? Measuring pass@N, verifier false-accept rate, and the latency/VRAM cost of getting there.
Numbers so far (16K context)
Peak GPU memory
BF16: 21.05 GiB · NF4: 11.50 GiB — NF4 leaves most of a 24GB card free for other work.
Decode speed
NF4 ran 13–20% faster than BF16 across 2K–16K context.
Concurrent candidates
BF16: ~4 · NF4: ~16 — roughly 4× the candidate-generation headroom on the same GPU.
Quality (144-task benchmark)
NF4 −2.8 points vs. BF16 (95% CI: −6.9 to +1.4) — not conclusively worse, but specific regressions in string handling reproduced on replay.
Design decisions
Why objective verification
Prefer unit tests, exact-match, JSON Schema, and deterministic checks over letting a model grade its own answers — especially for an agent where a wrongly accepted candidate could go on to execute an action.
Why separate semantic from formatting
Early NF4 "wins" turned out to be formatting differences, not better reasoning. Rescored everything so markdown fences and cosmetic style stop dominating the result.
Why re-order the roadmap
Vocabulary pruning was next on paper, but Phase B raised a bigger unanswered question: does the memory NF4 already recovered convert into real reliability? Moved verification ahead of further compression.
Why deprioritize INT8
Stuck around 14 tok/s on this stack — no memory or speed edge over BF16 or NF4, so not worth the added complexity right now.
Open questions
Unresolved
Can verified NF4 inference-time scaling (multiple candidates + a verifier) actually beat single-sample BF16 on one RTX 3090? That's the central Phase C experiment, still running.
Considering
NF4 doesn't have to win as a single-inference model to win as a generator — it's plausible that BF16 alone beats NF4 alone, while verified NF4×5 beats BF16 alone. That split is the interesting result if it holds up.
What's next
Where it stands
BF16 N=1 is still the stronger single-inference reference. NF4 isn't a free win on its own — it's a trade: a small, not-fully-resolved quality cost for roughly double the speed, half the memory, and 4× the candidate budget.
Working hypothesis
Use NF4's efficiency to generate more attempts, and let an executable verifier decide which attempt earns the right to act — turning a fixed 24GB GPU into a systems-design problem rather than a pure modeling one. Semantic career matching · COTF · build log shipped
Pipeline — 4 stages
Stage 1 · Text encodingsentence-transformers · all-MiniLM-L6-v2
Career title, industry description, skills, and tags concatenated into one document string. User input is the query. Browser-mode uses BM25 + synonym expansion offline; backend mode uses real embeddings via FastAPI on a local GPU server.
↓
Stage 2 · Cosine similarityvectors in high-dimensional space
Documents and query represented as vectors. Cosine similarity measures the angle between them — 0° is identical meaning, 90° is unrelated. Handles paraphrasing: "I like fixing machines" and "preventive maintenance" end up pointing in roughly the same direction even with no shared words.
↓
Stage 3 · MMR re-rankingMaximal Marginal Relevance
Pure cosine similarity clusters top results — all engineering roles if you mention engineering. MMR fixes this: each next result maximises λ × (relevance to query) − (1−λ) × (similarity to already-selected results). λ exposed as a UI slider. Lower λ = more diverse results across industries.
↓
Stage 4 · Resultsranked cards with match explanation
Cards show match score, NAICS code, skills, education pathways, and a "why this matched" explanation row. Backend mode returns richer explanation strings from the API.
