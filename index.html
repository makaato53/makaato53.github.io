Architecture — 3 layers

Layer 1 · Interface LiteLLM · Ollama · Web UI
LiteLLM as model gateway — routes tasks to the right model. Code → Qwen 2.5. Reasoning → DeepSeek. Review → Gemma. Generation → Llama 3. Local via Ollama, cloud SOTA as fallback. HTTP API not Docker socket.
↓
Layer 2 · Agent runtime LangGraph · Supervisor pattern
LangGraph manages the loop: task in → agent asks model → model picks tool → Python executes → results loop back → model decides next step → final answer. Supervisor node with tool executor, reviewer, and final. Handles state, retries, branching, memory.
↓
Layer 3 · Memory (RAG) ChromaDB · BM25 · sentence-transformers
Hybrid retrieval: embeddings for semantic/meaning similarity, BM25 for exact terms, config names, filenames, experiment IDs. Query → BM25 search → vector search → fuse results. 4 collections: agent traces, tool results, project docs, task results. Persistent to disk.

Design decisions

Why hybrid retrieval
Embeddings good at meaning similarity and natural language. BM25 good at exact keywords — config names, file paths, experiment IDs. Neither alone is enough.
Why LangGraph over raw loop
Stateful interaction, shared state across nodes, retries and branching built in. Higher abstraction — manage steps not individual calls.
Why HTTP API for Ollama
No security risk from Docker socket exposure. Cleaner service boundary. More production-like than daemon access.
3 generic agents + plugins
Core agents: repair, geography, general. Domain-specific logic lives in plugins not agents — keeps the core clean and extensible.

Open questions

Unresolved How much of agent reliability comes from architecture vs prompt quality? Structured-output enforcement helps — ambiguous prompts compound across steps. Still figuring out where to draw that line.
Considering Turbopuffer as vector store replacement for ChromaDB — better for sub-10M vector loads, runs on CPU, 16x compression. ChromaDB system RAM is a hard upper bound at scale.
Semantic career matching · COTF · build log shipped

Pipeline — 4 stages

Stage 1 · Text encoding sentence-transformers · all-MiniLM-L6-v2
Career title, industry description, skills, and tags concatenated into one document string. User input is the query. Browser-mode uses BM25 + synonym expansion offline; backend mode uses real embeddings via FastAPI on a local GPU server.
↓
Stage 2 · Cosine similarity vectors in high-dimensional space
Documents and query represented as vectors. Cosine similarity measures the angle between them — 0° is identical meaning, 90° is unrelated. Handles paraphrasing: "I like fixing machines" and "preventive maintenance" end up pointing in roughly the same direction even with no shared words.
↓
Stage 3 · MMR re-ranking Maximal Marginal Relevance
Pure cosine similarity clusters top results — all engineering roles if you mention engineering. MMR fixes this: each next result maximises λ × (relevance to query) − (1−λ) × (similarity to already-selected results). λ exposed as a UI slider. Lower λ = more diverse results across industries.
↓
Stage 4 · Results ranked cards with match explanation
Cards show match score, NAICS code, skills, education pathways, and a "why this matched" explanation row. Backend mode returns richer explanation strings from the API.

Bugs found mid-build

Substring synonym collision
"ai" matched inside "air", "maintenance", "training". Plain string .replace() corrupted queries silently. Fixed with word-boundary regex — \bai\b instead of "ai".
Stopwords eating intent
"like", "enjoy", "love", "want" — the most natural ways a user expresses preference — were all in the stopword list. Stripped silently. "I do not like welding" became identical to "I like welding".
Match % always 100% for rank 1
Score normalised to top result, so rank 1 always showed 100% — even a weak match. A zero-match query produced NaN%. Replaced with qualitative labels: Strong / Good / Possible.
MMR diversity over-inflated
Inter-document similarity used bigrams in Jaccard, making all careers look more distinct than they were. MMR under-penalised similarity. Fixed: Jaccard on unigrams only.

Architecture decision

Browser vs backend Browser mode (BM25 + synonym expansion) is a working offline fallback — no API key, no server needed. Backend mode (sentence-transformers via FastAPI) is the real thing. The right production path: HTML is a UI shell, the backend does all matching, browser JS shows a clear "semantic matching unavailable" warning rather than silently degrading.
